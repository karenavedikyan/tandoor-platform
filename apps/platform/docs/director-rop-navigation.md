# Навигация директора и РОПа (группы в sidebar / mobile)

## Зачем группы

Пункты меню сгруппированы по **рабочим сценариям**, а не списком страниц: сначала рабочий стол и территория, затем **клиентская база**, блок **продаж и KPI**, **инструменты** и отдельно разделы **в разработке**. Так быстрее выбрать контур: база, план-факт, задачи или справочные экраны.

## Структура (директор и РОП одинаково)

| Группа | Пункты |
|--------|--------|
| **РАБОЧИЙ СТОЛ** | Главная, Карточка территории |
| **КЛИЕНТСКАЯ БАЗА** | Клиенты (+ счётчик), Торговые точки (+ счётчик), Карта клиентов, Актуализация базы |
| **ПРОДАЖИ И KPI** | План-факт продаж, Аналитика команды, Задачи по витрине |
| **ИНСТРУМЕНТЫ** | Каталог, Обучение |
| **В РАЗРАБОТКЕ** | Коммуникации, Маркетинговые брифы |

Счётчики клиентов и ТТ считаются так же, как раньше (scope по роли в данных актуализации).

## Что видит директор

Тот же набор групп; домашняя по умолчанию остаётся **`/territory-card`** (`defaultHomePathForRole`). Доступ к маршрутам по-прежнему через `canAccessPath`.

## Что видит РОП

Та же группировка, что у директора. Добавлен доступ к **`/territory-card`** в `canAccessPath` для роли `team_lead`, чтобы пункт «Карточка территории» был согласован с меню.

## Что не менялось для менеджера (и прочих ролей)

- **Менеджер** (`sales_manager`): плоский список пунктов и прежние `data-testid` вида `nav-main`, `nav-dealer-base`, … без групп.
- **Маркетолог** и **аналитик**: без изменения логики списков.

## Разделы «В разработке»

Для директора и РОПа пункты **Коммуникации** и **Маркетинговые брифы** ведут на **`/feature-in-development?feature=…`** и страницу-заглушку `FeatureInDevelopmentPage` (спокойный текст, кнопка «Вернуться на главную», «Оставить пожелание» disabled до появления канала обратной связи).

Прямые ссылки на **`/communications`** и **`/marketing-briefs`** по-прежнему разрешены политикой доступа, если пользователь откроет их вручную; в меню для директора/РОПа показан сценарий заглушки.

## Техническая реализация

- Модель: `getPilotNavigation` → `PilotNavigationModel` (`layout: "flat" | "grouped"`) в `auth-access.ts`.
- UI: `AppShell` ренерит `NavigationPanel` (плоский список или группы с заголовками и стилями `#222631` / `#8F96B0` / `#9ACA3C` для активного пункта в группированном режиме).
- `getPilotNavItems` оставлен как **плоское объединение** групп для обратной совместимости (иконки rail строятся из плоского списка).

## Раскрываемые группы (аккордеон)

Поведение **только** для `layout: "grouped"` (роли `sales_director` и `team_lead`). Плоское меню менеджера, маркетолога, аналитика и остальных ролей не затрагивается.

### Раскрытие по умолчанию (если в `localStorage` ещё нет сохранённых предпочтений)

| Группа | По умолчанию |
|--------|----------------|
| Рабочий стол | Всегда раскрыт, свернуть нельзя |
| Клиентская база | Раскрыта |
| Продажи и KPI | Раскрыта только если текущий маршрут принадлежит пункту этой группы; иначе свёрнута |
| Инструменты | Свернута, если нет активного пункта внутри |
| В разработке | Свернута, если нет активного пункта внутри |

### Автораскрытие активной группы

Если по текущему URL активен пункт из группы, эта группа **всегда показывается раскрытой**, в том числе после ручного сворачивания: при следующем переходе на маршрут внутри группы она снова раскроется. Пока пользователь на этом маршруте, группу по-прежнему можно свернуть вручную.

### Сохранение в `localStorage`

- Ключ: `tandoor-pilot-sidebar-open-groups-v1`
- Значение: JSON-объект с флагами «группа раскрыта» по ключам групп (`workspace`, `client-base`, …).
- Чтение и запись только на клиенте (`useLayoutEffect` / обработчик клика), без обращения к `localStorage` при SSR.
- Состояние синхронизируется между десктопным sidebar и mobile sheet (общий стейт в `AppShell`).

## Test id групп и пунктов

См. `data-testid` в коде: `nav-group-workspace`, `nav-group-client-base`, `nav-group-sales-kpi`, `nav-group-tools`, `nav-group-in-development`, а также `nav-item-home`, `nav-item-clients`, …
