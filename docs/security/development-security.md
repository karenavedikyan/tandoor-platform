# Безопасная разработка Tandoor Platform

## 1. Цель документа

Зафиксировать постоянные правила разработки единой платформы Tandoor для клиентов и дилеров, менеджеров, регионалов, руководителей и других отделов при интеграциях с **1С**, **Bitrix**, **Bitrix24**, **Excel и Google-источниками** и текущим **Bitrix-сайтом**, так чтобы **публичный** репозиторий не становился местом хранения секретов и реальных данных, а production-контуры оставались защищёнными.

## 2. Какие репозитории могут быть публичными

1. **[tandoor-platform](https://github.com/karenavedikyan/tandoor-platform)** — может быть **публичным** только как **очищенный dev/prototype**: код без секретов, документация, демо-данные, `.env.example`.
2. **tandoor-bitrix** и любые репозитории с **production-кодом Bitrix**, кастомизациями боевого портала и реальными конфигурациями — **только приватные**.
3. Репозитории с **выгрузками 1С**, **дампами БД**, **логами** и **реальными персональными данными** — **не создаются как публичные**; если артефакт нужен команде, он хранится вне git или в закрытом хранилище с контролем доступа.

## 3. Что запрещено хранить в git

1. Реальные клиентские и персональные данные: ИНН, телефоны, email, адреса.
2. Реальные заказы, рекламации, договоры и документы клиентов.
3. Файлы **Excel/CSV** и прочие выгрузки с реальными данными.
4. Логи приложений и интеграций, дампы БД, бинарные снимки окружений.
5. Файл `.env` с реальными значениями, API-ключи, пароли, приватные ключи.
6. URL и секреты **Bitrix24 webhooks**, токены интеграций **Bitrix**.
7. Учётные данные **1С**, **FTP/SFTP**, строки подключения к production.
8. Production-конфигурации целиком (допустимы обезличенные шаблоны).

Правило распространяется на **все ветки и историю** репозитория: случайный коммит не отменяет риск до ротации секретов и очистки истории при необходимости.

## 4. Что разрешено хранить в публичном репозитории

1. Исходный код и тесты без встроенных секретов.
2. Документация (стратегия, архитектура, backlog, ADR).
3. **Фиктивные** демо-данные и сиды, явно помеченные как нереальные.
4. `.env.example` с именами переменных и плейсхолдерами.
5. Схемы API и контракты **без** реальных endpoint-секретов в примерах.

## 5. Секреты и ENV

1. Локально: собственный `.env` (в `.gitignore`), значения не коммитить.
2. **GitHub Secrets** — для CI/CD и автоматических проверок.
3. **Vercel Env** (или аналог) — для preview и production деплоев приложения.
4. Закрытые серверные хранилища и корпоративные менеджеры секретов.
5. Секреты интеграций **1С**, **Bitrix**, **Bitrix24**, **Google** задаются в соответствующих системах и окружениях, а в коде используются только имена переменных окружения.

## 6. Реальные данные и демо-данные

1. Для разработки в публичном репозитории используются **только** синтетические или обезличенные наборы.
2. Копирование production-данных в личные машины и в git **запрещено** без отдельного согласованного процесса (обезличивание, отдельное хранилище, NDA).
3. Импорты из **Excel/Google** в репозиторий не коммитить; допустимы скрипты и форматы **без** прикреплённых файлов с PII.

## 7. Gitignore policy

В корневом `.gitignore` (и при необходимости в приложениях) должны быть предусмотрены как минимум:

1. `.env`, `.env.local`, `.env.*.local`.
2. Каталоги логов: `logs/`, `*.log`.
3. Дампы: `*.sql`, `*.dump`, типичные имена бэкапов (по согласованию с командой).
4. Локальные БД разработчика, если не являются частью демо-репозитория по политике.
5. Выгрузки: `*.xlsx`, `*.csv` в рабочих каталогах импорта — по политике команды (по умолчанию не коммитить рабочие файлы с данными).

Периодически проводить аудит: нет ли в индексе файлов, которые должны игнорироваться.

## 8. Secret scanning policy

1. Включить **secret scanning** на уровне GitHub (или эквивалента) для организации/репозитория.
2. Локально и в CI по договорённости: **gitleaks**, **detect-secrets** или аналог с фиксированной конфигурацией.
3. Любое срабатывание на **main** и защищённых ветках блокирует merge до разбора.
4. Обучение команды: не вставлять ключи в URL, комментарии и тестовые фикстуры.

## 9. CI/CD проверки

Минимальный набор для пайплайна изменений в платформе:

1. `install` / `build`.
2. `lint` и `typecheck` (если применимо к стеку).
3. Проверка отсутствия секретов (встроенный сканер или **gitleaks** в job).
4. Запрет merge при падении критичных шагов.

Preview-деплои используют **отдельные** переменные окружения и не подтягивают production-строки подключения к **1С** или боевому **Bitrix**.

## 10. Работа с интеграциями 1С / Bitrix / Bitrix24 / Google

1. Ключи, пароли и webhook-секреты — только в ENV и менеджерах секретов; в коде — вызовы через конфигурацию окружения.
2. Для **Bitrix24** входящие webhook-URL считаются секретом; не публиковать в issue, PR и wiki без маскирования.
3. Для **1С** обмены настраиваются на стороне 1С и сервера интеграции; в git — только описание протокола и схемы полей.
4. Для **Google** — сервисные аккаунты и OAuth в закрытом хранилище; JSON ключей сервисного аккаунта не коммитить.
5. **Bitrix-сайт**: публичный репозиторий платформы не заменяет репозиторий сайта; связь через API и согласованные контракты данных.

## 11. Бэкапы и восстановление

1. Резервные копии БД и файлов хранятся **вне** git, в инфраструктуре с контролем доступа и шифрованием по политике компании.
2. Восстановление из бэкапа не должно приводить к копированию дампа в репозиторий.
3. Сроки хранения и ответственные роли фиксируются вне данного документа (IT / безопасность).

## 12. Preview mode для тестировщиков

Внешним тестировщикам показывается только согласованный этап; лишние MVP-разделы скрываются из навигации. Подробно: [Preview-режим Tandoor Platform](../architecture/preview-mode.md).

## 13. Правила перед каждым PR

Автор PR подтверждает (вручную или через чек-лист в шаблоне PR):

1. В диффе нет `.env`, логов, дампов, файлов с реальными данными.
2. Нет новых хардкод-секретов; новые переменные описаны в `.env.example`.
3. При необходимости приложены ссылки на задачу и тип данных (демо / синтетика).
4. Прогнан локально минимум: линтер и быстрый поиск по диффу на типичные паттерны секретов.

## 14. Incident response, если секрет попал в git

1. **Немедленно отозвать** скомпрометированный токен, **webhook** или ключ (Bitrix24, Google, 1С, FTP и т.д.).
2. **Перевыпустить** секрет в системе-источнике и обновить значения в **GitHub Secrets** / **Vercel Env** / серверах.
3. **Удалить** секрет из текущего кода и открытых веток; не оставлять «закомментированным».
4. При публикации в публичную историю — **очистить git history** (force-push, BFG, поддержка GitHub) по процедуре владельца репозитория.
5. **Проверить логи доступа** затронутых систем на предмет несанкционированного использования.
6. **Задокументировать** инцидент: что утекло, какие действия выполнены, дата, ответственный.

После инцидента обновить политику или автоматизацию (hook, CI), чтобы снизить риск повторения.
