# Preview-режим Tandoor Platform

## 1. Зачем нужен preview mode

Единая платформа объединяет сценарии для **клиентов и дилеров**, **менеджеров**, **регионалов**, **руководителей** и других ролей при интеграциях с **1С**, **Bitrix**, **Bitrix24**, **Excel/Google** и текущим **Bitrix-сайтом**. Параллельно в кодовой базе живут **несколько этапов** MVP и внутренних прототипов.

**Preview mode** нужен, чтобы:

1. Показывать тестировщикам и заказчикам **только актуальный**, согласованный этап.
2. Не создавать впечатление, что **незрелые** демо-функции уже готовы к промышленной работе.
3. Сохранять **весь внутренний каркас** наработок (ЛК продаж, регионала, задач, целей, импорта, карточек дилеров и др.) в репозитории без удаления кода.

## 2. Чем отличается internal prototype / preview / beta / production

| Статус | Назначение | Кто видит в продуктовой навигации |
|---|---|---|
| **internal_prototype** | Внутренний каркас, черновой UI, эксперименты | Только команда разработки; **не** показывается внешним тестировщикам через основное меню |
| **preview** | Согласованный срез для приёмки этапа | Внешние тестировщики **по списку** и сценарию этапа |
| **beta** | Расширенная выборка пользователей, сбор обратной связи | Ограниченная группа; явные оговорки о статусе «бета» |
| **production** | Промышленная эксплуатация | Все пользователи согласно ролям и правам |

**Внешним тестировщикам** допускается показывать только модули (или экраны) в статусах **preview**, **beta** или **production** — и только то, что перечислено в чек-листе этапа.

## 3. Что видят тестировщики

1. Пункты навигации и страницы, явно включённые в **текущий этап** приёмки.
2. Демо-данные или обезличенный стенд по правилам этапа.
3. Действия в рамках разрешённого сценария (например, только чтение или создание тестовых сущностей).

## 4. Что скрыто от тестировщиков

1. Модули и разделы в статусе **internal_prototype** — по умолчанию **скрыты из навигации** для роли внешнего тестировщика.
2. «Лишние» MVP-экраны, не входящие в перечень этапа.
3. Административные и отладочные инструменты без отдельного разрешения.

Демо-страницы при этом могут оставаться доступны **команде** по прямой ссылке или внутренней сборке — без публикации в меню для внешней аудитории.

## 5. Как текущие MVP-наработки используются как внутренний каркас

1. **Визуально** для внешних участников навигация может начинаться с **чистого листа**: только актуальный этап.
2. **Технически** существующие наработки (ЛК продаж, регионала, задачи, цели, импорт, карточки дилеров и т.д.) **не удаляются** — они остаются кодовой и архитектурной основой для следующих релизов.
3. Переключение видимости — через конфигурацию **preview**, **RBAC** и согласованные флаги, а не через удаление файлов.

## 6. Как переводить модуль из internal_prototype в preview

1. Закрытые критерии готовности этапа (функциональность, данные, безопасность).
2. Обновление паспорта модуля: статус видимости, список экранов, разрешённые действия.
3. Согласование списка тестировщиков и учётных записей.
4. Включение пунктов навигации для соответствующих ролей.
5. Краткая заметка в release notes / внутреннем журнале этапов.

## 7. Правила для навигации

1. Один источник правды по тому, **какие пункты меню** видит роль (конфиг, RBAC, feature flags).
2. Запрещено дублировать «скрытые» разделы в продакшен-меню «на всякий случай».
3. Для внешних тестировщиков — отдельная роль или tenant с урезанным меню.

## 8. Правила для демо-данных

1. Только **фиктивные** имена, ИНН, телефоны и адреса; или явная синтетическая схема.
2. Не использовать копии production-таблиц без обезличивания.
3. Демо-набор документируется: версия, владелец, сценарии проверки.

## 9. Переход к полноценной RBAC-модели

1. **Preview mode** — временный слой скрытия навигации и флагов до выравнивания прав по всем модулям.
2. Целевое состояние: **RBAC** на уровне сущностей и действий (чтение, создание, согласование, экспорт), единый журнал.
3. После стабилизации RBAC флаги «только для внутренней команды» сворачиваются в обычные права ролей, а статусы **preview** / **beta** используются для продуктового раската, а не как замена безопасности.
