# Архитектурные принципы

## 1. Платформа, а не набор кабинетов

Экосистема Tandoor должна развиваться как единая платформа с общими сущностями и ролевыми интерфейсами, а не как несколько независимых личных кабинетов.

## 2. Сохранение существующего контура

Публичный сайт, каталог, корзина и текущий клиентский контур не должны ломаться при запуске новой платформы.

Новые модули подключаются через:

1. API-слой.
2. События.
3. Слой совместимости.
4. Параллельный запуск.
5. Постепенную миграцию сценариев.

## 3. Общие сущности

Модули должны работать с единым словарем сущностей:

1. Организация.
2. Пользователь.
3. Роль.
4. Контрагент.
5. Дилер.
6. Товар / SKU.
7. Заказ.
8. Резерв.
9. Отгрузка.
10. Документ.
11. Рекламация.
12. Маркетинговая кампания.
13. Задача.
14. Уведомление.
15. Склад.
16. Логистический маршрут.

## 4. API-first

Каждый модуль должен иметь понятные API-контракты для чтения и изменения данных.

API нужен для:

1. Интеграции с сайтом.
2. Интеграции с ERP и складскими системами.
3. Подключения будущих мобильных сценариев.
4. Подключения BI и отчетности.
5. Безопасного расширения платформы.

## 5. Event-driven для статусов

Изменения ключевых объектов должны порождать события:

1. `order.created`
2. `order.status_changed`
3. `reserve.requested`
4. `reserve.confirmed`
5. `shipment.ready`
6. `shipment.dispatched`
7. `claim.created`
8. `claim.resolved`

События позволяют модулям реагировать друг на друга без жесткой связки.

## 6. Role-based UI

Пользователь видит только рабочее пространство, соответствующее его роли и организации.

Один пользователь может иметь несколько ролей.

## 7. Безопасность по умолчанию

Для всех модулей обязательны:

1. RBAC.
2. Разделение данных по организациям и юридическим лицам.
3. Журнал действий.
4. Защита документов и коммерческих условий.
5. Аудит критичных операций.

## 8. Модульность

Каждый модуль должен иметь:

1. Собственный паспорт.
2. Явные зависимости.
3. Собственные сценарии.
4. API-контракты.
5. События.
6. Критерии приемки.

Модуль можно разрабатывать и тестировать отдельно, но интегрировать только через общее ядро.

## 9. Текущие операционные источники (Google Workspace)

Google Таблицы, Google Документы и при необходимости Google Диск нужно учитывать как действующие источники данных и контента на период миграции в платформу.

Для каждого такого источника фиксируют:

1. Владельца и зону ответственности.
2. Направление обмена (только чтение, периодическая выгрузка, двусторонняя синхронизация).
3. Источник истины относительно ядра платформы и срок, когда Google перестает быть мастером.
4. Контроль доступа (рабочие аккаунты, сервисный доступ, аудит).

Интеграции с Google выполняют через официальные API или согласованный экспорт, с журналом ошибок и повторов, без «тихого» копирования неучтённых полей.

## 10. База знаний и обучение

Знания о продукте, продажах и работе с возражениями оформляют отдельным контуром с единым хранением, версиями и правами, а не только как вложения в маркетинговом модуле.

В состав контура входят:

1. Внутренняя Wiki по продукту.
2. Материалы для дилеров и для менеджеров с разными уровнями доступа.
3. Техника продаж, скрипты и сценарии работы с возражениями.
4. Подготовка к тестам и сертификации (в том числе как целевое состояние после накопления контента).

Контент публикуется через ядро (роли, организации, журнал), связан с уведомлениями и при необходимости с внешними черновиками в Google Документах до переноса в управляемую модель.
